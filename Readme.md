# Scalable and Cloud Computing project: Earthquake Co-Occurrence Analysis with Apache Spark

Distributed co-occurrence analysis of earthquake events using Scala and Apache Spark, executed on Google Cloud Dataproc.

---

# Project Objective

The goal of this project is to identify the pair of geographic locations that co-occurred most frequently within the same day in a large earthquake dataset.

For the pair with the highest number of co-occurrences, the application outputs:

* the two locations;
* the list of dates in chronological order.

The implementation follows a distributed MapReduce approach using Apache Spark and has been evaluated on multiple Google Cloud Dataproc cluster configurations.

---

# Dataset Processing Rules

The analysis follows the specifications provided in the project assignment.

## Spatial Aggregation

Earthquake coordinates are approximated by rounding latitude and longitude to one decimal place.

Example:

| Original Coordinates | Rounded Coordinates |
| -------------------- | ------------------- |
| 112.234, 81.593      | 112.2, 81.6         |
| 112.237, 81.596      | 112.2, 81.6         |
| 112.199, 81.622      | 112.2, 81.6         |

Each rounded coordinate pair represents a geographic cell.

---

## Temporal Aggregation

Only the day is considered.

Example:

```text
2025-01-01 00:00:01
2025-01-01 12:00:00
2025-01-01 23:59:59
```

are all mapped to:

```text
2025-01-01
```

---

## Duplicate Removal

After rounding coordinates and extracting the day, duplicate events occurring:

* in the same geographic cell;
* on the same day;

are removed.

This prevents artificial co-occurrences generated by multiple earthquakes occurring in the same location on the same day.

# Algorithm

The implementation is based on a distributed MapReduce workflow.

## Step 1 – Data Loading

The CSV dataset is loaded as an RDD using Spark:

```scala
val data = spark.read
  .option("header", "true")
  .csv(filename)
  .rdd
```

---

## Step 2 – Parsing and Normalization

For each earthquake event:

1. Latitude and longitude are parsed.
2. Coordinates are rounded to one decimal place.
3. The timestamp is reduced to its day component.

The resulting format is:

```text
(date, (latitude, longitude))
```

Example:

```text
("2024-03-12", (37.5, 15.3))
```

---

## Step 3 – Duplicate Removal

Duplicates are removed using:

```scala
distinct()
```

This guarantees that each location contributes at most once per day.

---

## Step 4 – Self Join

A self-join is performed on the date key:

```scala
parsedData.join(parsedData)
```

For each day, all pairs of locations active on that day are generated.

Conceptually:

```text
(date, locationA)
(date, locationB)
(date, locationC)
```

becomes:

```text
(A,B)
(A,C)
(B,C)
```

for that specific day.

---

## Step 5 – Removal of Symmetric Pairs

To avoid counting:

```text
(A,B)
(B,A)
```

twice, a lexicographic ordering is imposed.

The condition:

```scala
loc1Str < loc2Str
```

ensures that:

* only one ordering is retained;
* self-pairs `(A,A)` are discarded.

---

## Step 6 – Aggregation of Co-occurrences

Each valid pair is associated with the day in which it occurred:

```text
((locationA, locationB), [date])
```

Dates are aggregated using:

```scala
reduceByKey(_ ++ _)
```

obtaining:

```text
((locationA, locationB),
 [date1, date2, date3, ...])
```

---

## Step 7 – Selection of the Most Frequent Pair

The pair with the largest number of associated dates is selected:

```scala
sortBy(_._2.size, ascending = false)
```

followed by:

```scala
first()
```

---

## Output Format

Example:

```text
((37.5, 15.3), (38.1, 13.4))
2024-03-12
2024-04-01
2024-04-03
```

The dates are printed in ascending chronological order.

# Build

Move to the project directory:

```bash
cd ~/earthquake-project
```

Generate the fat JAR:

```bash
sbt clean assembly
```

The output artifact will be:


# Upload to Google Cloud Storage

```bash
gcloud storage cp \

gs://<YOUR_BUCKET>/

gcloud storage cp \
dataset-earthquakes.csv \
gs://<YOUR_BUCKET>/
```

---

# Program Arguments

The application accepts:

| Argument     | Description                         |
| ------------ | ----------------------------------- |
| dataset-path | URI of the dataset                  |
| partitions   | Optional number of Spark partitions |

Example:

```bash
EarthquakeCoOccurrence dataset.csv 32
```

If no partition count is specified, Spark uses its default partitioning strategy.

---

# Dataproc Cluster Creation

Example configuration with 4 workers:

```bash
gcloud dataproc clusters create mio-cluster \
  --region=europe-west1 \
  --num-workers=4 \
  --master-machine-type=n2-standard-4 \
  --worker-machine-type=n2-standard-4 \
  --master-boot-disk-size=240 \
  --worker-boot-disk-size=240
```

---

# Running the Job

Default Spark partitioning:

```bash
gcloud dataproc jobs submit spark \
  --cluster=mio-cluster \
  --region=europe-west1 \
  --class=EarthquakeCoOccurrence \
  --jars=gs://<YOUR_BUCKET>/EarthquakeCoOccurrence-assembly-1.0.jar \
  -- gs://<YOUR_BUCKET>/dataset-earthquakes.csv
```

Custom partitioning:

```bash
gcloud dataproc jobs submit spark \
  --cluster=mio-cluster \
  --region=europe-west1 \
  --class=EarthquakeCoOccurrence \
  --jars=gs://<YOUR_BUCKET>/EarthquakeCoOccurrence-assembly-1.0.jar \
  -- gs://<YOUR_BUCKET>/dataset-earthquakes.csv 32
```

# Performance Considerations

The most expensive operation of the application is the self-join used to generate all co-occurring location pairs for each day.

To reduce computational overhead:

* duplicates are removed before the join;
* repartitioning can be applied before processing;
* multiple partitioning strategies are evaluated.

The objective is to study the impact of cluster size and partition count on execution time and scalability.
